# FRDM-MCXN947 + VL53L0X: commented learning example

This standalone program initializes a VL53L0X, measures distance, and prints
valid readings in millimeters to the MCU-Link serial port. It runs on Cortex-M33
core 0 without FreeRTOS. It is stored beside your camera source in the
`vl53l0x_distance` subdirectory and has its own build output.

Assumption: your board is FRDM-MCXN947 and your module actually contains a
**VL53L0X**. A VL53L1X or another ToF chip needs a different driver. The label
"VL53L0XV2" does not establish the breakout manufacturer's power circuitry.

| File | What you learn |

| `CMakeLists.txt`, `prj.conf`, `build.ps1` | Selecting sources, SDK drivers and build tools |
| `vendor/st/api/core` | Actual ST sensor API, including its original documentation/comments |

Our application and adapter are commented throughout. The vendor implementation
is retained as supplied, with its existing comments and license notices. It has
thousands of lines of optical tuning and calibration logic; this guide explains
its boundaries and gives you entry points to study it without pretending each
internal tuning constant has been independently documented here.

## 2. Wiring before running

Disconnect USB/power while changing wires. Use the sensor alone for this first
test; remove camera/display shields that might occupy the selected pins.

| Breakout signal | FRDM-MCXN947 connection | Purpose |
| --- | --- | --- |
| SDA | J2 pin 18, MCU P4_0 | Bidirectional I2C data |
| SCL | J2 pin 20, MCU P4_1 | I2C clock generated by the MCU |
| GND | J2 pin 14 or another board GND | Shared voltage reference |
| VIN/VCC | Supply specified by your exact breakout | Powers sensor/module |
| XSHUT | Must be HIGH through the module's supported pull-up arrangement | LOW holds sensor in shutdown |
| GPIO1 / INT | Leave unconnected for this example | Optional measurement-ready output |

SDA/SCL/GND header locations come from the installed SDK's
`examples/_boards/frdmmcxn947/driver_examples/lpi2c/polling_b2b/master/example_board_readme.md`.
P4_0/P4_1 Alt2 selection comes from that example's `pin_mux.c`.
Count header pins using the board's pin-1 marker; MCU port numbers and connector
pin numbers are different numbering systems.

**Confirm the breakout's power input and level shifting before connecting it.**
This host configuration expects 3.3-V-compatible SDA/SCL. Do not pull those lines
to 5 V. A regulator on VIN does not automatically mean that SDA/SCL or XSHUT are
level shifted. If a module has level shifters, host-side pull-ups belong on the
host voltage domain; do not change sensor-side pull-ups blindly.
The bare ST chip's specifications are not a substitute for the module schematic.

I2C needs pull-ups: neither device actively drives HIGH in normal open-drain
operation. Check whether the breakout already includes them before adding more.
The internal MCU pull-ups configured here do not replace proper bus pull-ups.
Do not leave XSHUT floating if your module lacks its own pull-up. This program
does not control that pin; consult the module's allowed XSHUT voltage.

## 3. Build and load

### Dedicated ToF launch in VS Code

1. Use **File > Open Workspace from File...** and select
   `ToF-only.code-workspace` in this folder. The workspace includes only the ToF
   project so camera launch entries are not offered in this window.
2. Press **Ctrl+Shift+D** to open Run and Debug.
3. Select **ToF only - VL53L0X (MCXN947 core 0)** from the launch dropdown.
4. Connect the MCU-Link USB cable, then press **F5**. The prelaunch task runs
   `build.ps1`; if the build fails, fix it rather than choosing Debug Anyway.
   The debugger loads only `build/debug/vl53l0x_distance_cm33_core0.elf` and
   pauses at this project's `main.c`.
5. Open Serial Monitor on **COM4**, **115200 baud**, and start monitoring.
6. Press **F5** again to continue from `main()` and see startup/readings.
7. Press **Shift+F5** to end debugging. **Ctrl+Shift+B** builds without flashing.

The configuration is in `.vscode/launch.json`, with its build task in
`.vscode/tasks.json`. `skipBuildBeforeDebug` disables the extension's automatic
project build because our explicit `preLaunchTask` builds the ToF application.
The selected probe serial number and tool paths match your current installation;
update them if you switch probes or tool versions. Launching programs the board
and replaces its current application.

The folder is physically under the camera example for historical convenience,
but this CMake project does not compile the camera application, MPP, model or
FreeRTOS. It uses shared SDK board/startup/drivers and ST's sensor API. The new
workspace does not move or duplicate source files.

Open a PowerShell terminal in this `vl53l0x_distance` folder and run:

```powershell
powershell -ExecutionPolicy Bypass -File .\build.ps1
```

This launches only that PowerShell process with the script policy override; it
does not change the machine's permanent execution policy. The script uses your
currently installed MCUXpresso CMake, Ninja, Python environment and ARM GCC

Build products:


The ELF includes load addresses and debugger symbols. The BIN contains raw
firmware bytes. Use the ELF with an MCUXpresso/MCU-Link debug configuration for

an imported project first, import this folder as an existing CMake application
with the same board/core/toolchain settings; the script already builds it.
Your existing camera launch configuration may still point to the camera ELF:
select the new ELF explicitly before programming.

Connect USB to the board's **MCU-Link USB connector (J17)**. Open its virtual COM
port at **115200 baud, 8 data bits, no parity, 1 stop bit, no flow control**.
Then run the debugger or reset the programmed board. Firmware loading replaces
the application currently in MCU flash; camera source files remain available.

## 4. What happens before main()

Reset loads the initial stack pointer and reset handler from the vector table.
The SDK's startup assembly and C runtime prepare RAM, copy initialized variables
from flash, zero uninitialized static storage, and transfer control to `main()`.
The SDK supplies the vector table, chip definitions, linker memory map and
system initialization. Our application does not manually repeat that work.

Flash stores instructions and constants across power loss. RAM holds working
variables and loses its contents at power-off. The stack holds local call data;
a `static` object has storage lasting through the entire execution.

## 5. Follow main() step by step

1. `APP_InitHardware()` configures clocks, pins, UART and the I2C master.
2. `PRINTF()` sends startup text through UART4 to the MCU-Link USB bridge.
3. `sensor` holds ST's software state, its address and the selected controller.
4. A 10-ms delay allows boot time after power-up. It cannot release XSHUT.
5. Read register `0xC0` and require model ID `0xEE`; this tests actual I2C reads.
6. `VL53L0X_DataInit()` initializes software/device parameters. Our compile-time
   `USE_I2C_2V8` option selects ST's higher I/O-voltage mode instead of its
   1.8-V default. It does not provide regulation or level shifting.
7. `VL53L0X_StaticInit()` applies the API's initial tuning and configuration.
8. Reference SPAD management chooses reference light-detector settings.
9. Reference calibration establishes internal VHV/phase settings. This learning
   example performs these at boot rather than storing calibration in host flash.
10. Select single-ranging mode and a 33,000-us measurement budget.
11. Repeatedly request one measurement, check its status, print it, and pause.

The chip emits infrared light and measures its return timing. Physically,
distance is light speed multiplied by round-trip time divided by two. The
sensor's internal electronics perform this timing; the MCU does not time photons
with its I2C clock. I2C exchanges commands and finished results.

SPAD means single photon avalanche diode. VHV and phase calibration tune internal
operating settings; they are not user-selected distance offsets. Adding a cover
window or enclosure can require separate offset/crosstalk calibration. The API
contains those procedures, but this example does not perform them.

## 6. Clocks and pins are separate jobs

`BOARD_InitBootClocks()` sets the standard board CPU clock configuration.
`CLOCK_AttachClk()` connects a clock source to a peripheral. The 12-MHz FRO is
the source for UART4 and FLEXCOMM2; it is not the final I2C bus frequency.
`LPI2C_MasterInit()` computes peripheral timing for the requested 100-kHz bus.

The PORT controller selects which internal function appears at a physical pin.
`kPORT_MuxAlt2` selects different functions on different pins; consult the chip's
pin table or a known board example before choosing it. P4_0/P4_1 route to
FLEXCOMM2; P1_8/P1_9 route to FLEXCOMM4 UART.

LP_FLEXCOMM is a configurable peripheral block. The SDK's LPI2C initialization
selects its I2C personality. Clocking the block alone does not select its pins,
and routing pins alone does not initialize its protocol engine.

## 7. A measurement travels through these layers

```text
main.c: request a single measurement
    -> ST API: initialize/start/wait/read/interpret optical result
        -> our platform adapter: read/write sensor register bytes
            -> NXP LPI2C driver: operate MCU peripheral registers
                -> SDA/SCL wires -> VL53L0X
```

The adapter's transfer structure names the slave address, sensor register,
direction, data buffer and byte count. NXP's blocking transfer function performs
the bus transaction. Blocking means the CPU stays in the call until completion
or an error; it does not mean other tasks are scheduled, because no RTOS runs here.

For a register read the MCU first writes the register number, then issues a
repeated START and reads the requested bytes. The repeated START changes the
transaction direction without releasing the bus. ACK means a receiver
acknowledges a byte. A missing ACK often indicates power, address, wiring or
shutdown problems. The host normally NACKs the final read byte to end reception;
that normal protocol action is different from an unexpected error NACK.

`0x29` is the seven-bit device address. On the wire it becomes `0x52` for a write
and `0x53` for a read because the bottom bit selects direction. NXP's API expects
`0x29`; passing `0x52` as the address would shift the address incorrectly. This
adapter consistently stores the seven-bit form, even though some ST examples
store the eight-bit form. It does not support changing addresses at runtime.

A register is an addressable setting or result inside the sensor. It is not
the same thing as a C variable in MCU RAM. The adapter transfers values between
these two places. A pointer tells a function where to read/write RAM; it does not
itself transmit anything over I2C.

The sensor sends multi-byte values most-significant byte first. For example,
bytes `0x01, 0xF4` form `(0x01 << 8) | 0xF4 = 500`. Our adapter explicitly packs
and unpacks this order rather than depending on the MCU's memory byte order.
It casts to 32 bits before a 24-bit shift so the arithmetic has enough width.

`FixPoint1616_t` represents a fractional number multiplied by 65536. It is used
inside the API for rates/limits. The printed distance is already an integer in
millimeters; it does not require fixed-point conversion.

## 9. Two distinct checks protect every reading

An ST API error means the requested operation failed: for example, an I2C
transaction failed or completion timed out. `Check()` prints the operation,
ST description/code and last NXP I2C result, then stops. Reset retries startup.
The last I2C status is diagnostic context; ST can also fail for reasons unrelated
to that most recent transaction.

If the API succeeds, `RangeStatus` describes optical measurement quality.
Only zero is accepted here. A signal/sigma/phase/range failure is printed as
an invalid reading, and the loop continues. No invalid value is presented as
an obstacle distance, and zero is not used as a generic error sentinel.

`I2C_RETRY_TIMES=100000U` bounds certain NXP polling loops that otherwise wait
forever. It counts loop iterations, not milliseconds. ST's API independently
limits measurement-ready polling to 2000 iterations; our polling delay adds
1 ms per waiting iteration, plus I2C/processing time. These are different limits,
and neither is a precise overall deadline for the entire initialization routine.

## 10. Timing, troubleshooting and experiments

The loop duration includes ranging, I2C overhead, UART printing and the 200-ms
pause. With a 33-ms budget it is roughly a few readings per second, rather than
exactly five. `APP_DelayMs()` busy-waits and consumes CPU time. An eventual
FreeRTOS version can replace appropriate waits with task delays and add a mutex
for shared sensor/bus access; it requires coordination beyond copying this main.

| Symptom | First checks |
| --- | --- |
| No serial output | Correct MCU-Link connector/COM port, 115200 settings, new ELF loaded, debugger running |
| Model-ID read fails | Sensor power, shared ground, SDA/SCL swapped, header numbering, pull-ups, XSHUT |
| Model ID differs | Confirm actual sensor chip; VL53L1X needs a different driver |
| Initialization stalls or times out | Wiring, bus voltage, XSHUT, another board/shield driving these pins |
| API succeeds but range invalid | Start with a flat target nearby, clear optical window, moderate ambient light |
| Distance never changes | Move a flat target in front of the sensor's viewing area; ensure running new firmware |

Suggested learning exercises: change only `APP_PAUSE_MS` and observe output
frequency; print the raw range status; then add a threshold message for a valid
distance below 200 mm. Place that condition inside the valid-result branch so
invalid measurements never trigger the threshold. Keep the driver layer focused
on communication rather than putting application decisions there.

To study ST's internals, start with these functions and follow their calls:

| Vendor file | Role |
| --- | --- |
| `vl53l0x_api.c` | Public API, DataInit, StaticInit, single measurement orchestration |
| `vl53l0x_api_core.c` | Polling, low-level calculations and device configuration helpers |
| `vl53l0x_api_calibration.c` | Reference/offset/crosstalk calibration algorithms |
| `vl53l0x_api_ranging.c` | Ranging calculations/helpers |
| `vl53l0x_api_strings.c` | Human-readable error and result-status descriptions |
| `vl53l0x_tuning.h` | Vendor tuning settings; avoid editing unexplained constants |

## 11. Build-system details and references

CMake collects source files and invokes the SDK's board integration. Kconfig
(`prj.conf`) selects the LP_FLEXCOMM I2C driver and our custom hardware/pin setup.
The inherited hello_world board settings are followed by our configuration so
the example doesn't accidentally use hello_world's generated pin initialization.
Ninja schedules compiler commands. GCC compiles C into ARM object files; the
linker combines them with SDK startup/runtime code and maps them into flash/RAM.
The final ELF is converted into a BIN by the SDK build machinery.

The sensor API is included locally, pinned to a specific upstream revision, so
building does not require downloading it again. See `vendor/PROVENANCE.md`.

- [ST VL53L0X datasheet](https://www.st.com/resource/en/datasheet/vl53l0x.pdf): electrical interface, ToF, XSHUT and calibration overview.
- [ST sensor C API](https://www.st.com/en/embedded-software/stsw-img005.html): API purpose and platform-layer design.
- [Pinned API mirror](https://github.com/zephyrproject-rtos/hal_st/tree/066d2f481ce6c35a94730a3bc4bd05e9fb0e767c/sensor/vl53l0x): exact included driver.
